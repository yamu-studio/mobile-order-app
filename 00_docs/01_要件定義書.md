## 1. エグゼクティブサマリー

### 1.1 プロジェクト概要

架空の単一店舗カフェ「NOOK Coffee 中目黒店」（仮称）で、レジの対面注文をテイクアウト向けモバイルオーダーで補う想定とする。レジ対応の手戻りを減らせるかを仮説として扱い、決済は対象外とする。1ヶ月以内のリリース希望は架空案件の制約条件であり、本プロジェクトの実公開期限ではない。Phase1をMVPに限定し、会員機能等はPhase1.5以降の候補とする。

また、確定後の注文修正・取消、品切れ発生時の対応、および店舗側の役割分離（注文を受理するホールスタッフと、調理進行を管理する厨房スタッフ）をPhase1のMVPに含める（v1.1で追加）。将来的に店内飲食（イートイン）への対応拡張も見据えるが、Phase1ではテイクアウトのみを対象とする。

### 1.2 背景・課題

現状（As-Is）において、以下の課題が発生している：

| # | 課題 | 影響・深刻度 |
|---|------|------------|
| 1 | レジでの対面注文のみのため、スタッフがレジ対応に張り付き、他の調理・接客業務に人手を割けない | 高：人件費増・オペレーション逼迫 |
| 2 | 注文受付・カスタマイズ確認をレジで都度口頭で行うため、1人あたりの対応時間が長くなり、ピーク時に行列が発生しやすい | 中：機会損失（離脱客発生の可能性） |
| 3 | メニュー変更（価格改定・季節限定品の入替）に迅速に対応する手段がない | 中：販売機会の損失 |
| 4 | 注文の修正・取消・品切れ発生時、口頭での再確認・伝達に頼っており、伝達漏れが起こり得る | 中：誤提供・顧客対応の遅延（v1.1で追加） |

> 上記の課題は架空シナリオの仮説であり、実店舗への聞き取り結果ではない。ピーク時待ち時間・レジ対応時間・行列による離脱客数などの実測値は存在しない。

### 1.3 目的・期待効果

本システム導入により、以下を実現する：

| 目的 | 現状（KPI） | 目標（KPI） | 計測方法 |
|------|------------|------------|---------|
| レジ対応工数の削減 | レジスタッフが注文受付・カスタマイズ確認・会計を一貫して対応（所要時間未計測） | モバイル経由注文比率50%以上を目安（要確認） | 注文経路別（モバイル／レジ）の件数集計 |
| ピーク時の行列緩和 | ピーク時に行列が発生（体感、未計測） | ピーク時のレジ対応時間短縮（具体目標はリリース後の実測を踏まえ設定） | 店舗スタッフの目視・簡易計測 |
| メニュー変更の迅速化 | 価格改定・季節メニュー入替に外部依頼が必要な場合がある | オーナー自身が管理画面から即時反映 | 管理画面の更新ログ |
| 注文修正・品切れ対応の伝達漏れ削減 | 口頭での再確認・伝達に依存（伝達漏れが起こり得る） | 修正・取消・品切れ対応をシステム上で一元管理し、変更履歴として追跡可能にする | 変更履歴ログの記録件数・対応漏れの有無 |

### 1.4 スコープ定義

**対象範囲（In Scope・Phase1）：**
- 客向け：メニュー閲覧・カテゴリ絞込、商品カスタマイズ（サイズ・ミルク種類等）、アレルゲン情報表示、カート機能、注文内容確認、匿名での注文確定（決済なし）、受け取りステータス確認、**確定後（受理前）の注文内容修正・取消**（v1.1で追加）
- ホールスタッフ向け：**新規注文・修正/取消依頼の確認、注文の受理、品切れ発生時の該当注文ハイライト表示、変更履歴の閲覧**（v1.1で追加・再定義）
- 厨房スタッフ向け：**受理済み注文の調理進行管理（キッチンディスプレイ）**（v1.1でホールスタッフ機能と分離）
- オーナー向け：簡易メニュー管理画面（商品・価格・オプション・在庫状態・アレルゲン情報の登録編集）

**対象外範囲（Out of Scope・Phase1）：**

| 除外項目 | 除外理由 | 対応予定 |
|---------|---------|---------|
| オンライン決済機能 | 店頭決済を維持する方針、決済導入に伴う追加コスト・審査期間を回避するため | Phase2以降で必要性を再検討 |
| 会員登録・ログイン・注文履歴 | 1ヶ月納期の中でMVPを優先するため | Phase1.5（Phase1完了後、目安1ヶ月） |
| ポイント・特典制度 | 会員基盤確定後でないと設計できないため | Phase2 |
| プッシュ通知（Web Push） | 画面上のステータス表示で運用可能と判断したため優先度を下げた | Phase2以降で再検討 |
| 複数店舗対応（マルチテナント化） | 今回は単一店舗導入が対象 | Phase2（他店舗展開が具体化した時点） |
| POSレジとの自動連携 | 今回はキッチンディスプレイでの目視確認運用とする | 運用開始後の実態を踏まえて要否判断 |
| 店内飲食（イートイン）対応 | 初期リリースはテイクアウトに集中する方針としたため（v1.1で明記） | 将来、卓番号方式での拡張を想定（時期未定、Phase2以降で再検討） |
| 実店舗運用面の検証（通信障害時対応・混雑時の実地検証・スタッフ教育・衛生管理運用） | 本プロジェクトの検証範囲外と位置付けているため（v1.1で明記、9.3参照） | 実運用開始後、必要に応じて別途検証 |

> 補足（v1.1）：アレルゲン情報表示（F-003）・在庫状態切替（F-022）は実装負荷が比較的小さいと判断し、Phase1のMustとして維持する（当初案の据え置き）。

## 3. 業務フロー

### 3.1 現状業務フロー（AS-IS）

```
[手順1] 客が来店しレジ前で並ぶ（ピーク時：行列発生）
   ↓
[手順2] レジスタッフが口頭で注文内容・カスタマイズ（サイズ・ミルク種類等）をヒアリングしながらレジに入力（所要時間：未計測）
   ↓
[手順3] その場で会計
   ↓
[手順4] 注文内容を口頭または紙でキッチンに伝達、調理
   ↓
[手順5] 完成後、レジ横で客に呼びかけて受け渡し
```

**課題詳細：**
- レジスタッフが「注文受付」「カスタマイズ確認」「会計」を1人で担うため、1件あたりの対応時間が長くなりやすい
- ピーク時に行列が発生し、離脱（並ばずに帰る）客が発生している可能性がある（要計測）
- キッチンへの伝達が口頭・紙のため、伝達ミス・確認の手間が発生しうる
- 注文の修正・取消・品切れが発生した場合、関係者間の再確認・伝達が口頭に頼っており、伝達漏れが起こり得る（v1.1で追加）

### 3.2 将来業務フロー（TO-BE）

```
[手順1] 客がスマートフォンでモバイルオーダー画面にアクセス（導線の詳細は設計フェーズで検討）
   ↓
[手順2] メニューを閲覧し、サイズ・ミルク種類等をカスタマイズしてカートに追加
   ↓
[手順3] 注文内容を確認し、注文を確定（状態：受付済→確認中。会計は行わず、店頭で会計を実施）
   ↓
[手順3a・分岐] 「確認中」の間、客は注文内容の修正・取消を行うことができる（変更履歴に記録）
   ↓
[手順4] ホールスタッフが受注確認画面で新規注文・修正内容を確認し、受理（状態：確認中→調理中）。受理と同時にキッチンディスプレイへ調理指示が反映される
   ↓
[手順4a・分岐] 受理対象の商品が品切れの場合、ホールスタッフが該当注文のハイライト表示を確認し、代替提案・修正依頼・取消等の顧客対応を行う
   ↓
[手順5] 厨房スタッフが調理を進行する
   ↓
[手順6] 客は店頭で会計・受け取り、提供完了後に状態を「提供済み」へ更新する
```

調理完了から受け渡しまでの通知方法と、「提供済み」更新の担当・タイミングは未決であり、設計Issueで確定する。現行の5状態に「受け取り可能」は含めない。

### 3.3 業務フロー変更点サマリー

| 変更点 | AS-IS | TO-BE | 効果 |
|-------|-------|-------|------|
| 注文受付 | レジでの口頭受付 | スマホでのセルフ入力 | レジ対応時間の削減 |
| カスタマイズ確認 | 口頭でのヒアリング | 画面での選択式入力 | 聞き間違い防止・レジ時間短縮 |
| キッチンへの伝達 | 口頭・紙 | キッチンディスプレイへの自動反映 | 伝達ミス削減・調理準備の効率化 |
| メニュー更新 | 外部依頼を要する場合がある | オーナーが管理画面から随時更新 | 迅速な価格改定・季節メニュー対応 |
| 注文の修正・取消 | 口頭での再確認・伝達（伝達漏れが起こり得る） | アプリ上で修正・取消し、変更履歴として記録（v1.1） | 伝達漏れの防止・修正内容の追跡可能化 |
| 受理・調理の役割分担 | レジ担当が受付から会計まで兼務、厨房への伝達も口頭 | ホールスタッフが受理判断、厨房スタッフが調理進行を担当（役割分離、v1.1） | 責任範囲の明確化・伝達ミス防止 |
| 品切れ対応 | 口頭でその場対応、伝達漏れの可能性 | 品切れ発生時に該当注文をシステム上でハイライトし、ホールスタッフが対応（v1.1） | 対応漏れの防止 |

**F-002：商品詳細・カスタマイズ選択**

| 項目 | 内容 |
|------|------|

**F-008／F-009：注文修正・取消（客側、v1.1で新設）**

| 項目 | 内容 |
|------|------|
| 対象状態 | 「受付済」「確認中」の間のみ操作可能。「調理中」以降は不可（ホールスタッフ経由の対応に切り替える） |

| 記録 | 修正・取消の都度、変更履歴（F-013／OrderStatusLog）に記録する |
| 反映 | 修正・取消が発生した場合、ホールスタッフの受注確認画面（SCR-005）に即時反映される |

**F-011：注文受理（ホールスタッフ、v1.1で新設）**

| 項目 | 内容 |
|------|------|
| 操作 | 新規注文または修正済み注文の内容を確認し、「受理」操作で「確認中」→「調理中」へ遷移させる |
| 効果 | 受理と同時にキッチンディスプレイ（SCR-006）に調理指示として反映される |
| 制約 | 受理後は客側の自己修正・自己取消（F-008／F-009）は対象外となる |

**F-012：品切れ警告（ホールスタッフ、v1.1で新設）**

| 項目 | 内容 |
|------|------|
| トリガー | オーナーがメニュー管理画面（F-022）で商品を「売り切れ」に切り替えた時点 |
| 動作 | 当該商品を含む未完了注文（受付済／確認中／調理中）を受注確認画面上でハイライト表示する |
| 対応 | ホールスタッフが代替品提案・修正依頼・取消のいずれかを選び、顧客対応を行う（具体的な対応手順は運用マニュアルで別途整備、TBD） |

**F-015／F-016：キッチンディスプレイ（厨房スタッフ、v1.1で役割分離）**

| 項目 | 内容 |
|------|------|
| 表示内容 | 「調理中」ステータスの注文のみを受理時刻順に一覧表示。受付番号・商品明細（オプション含む）・経過時間 |
| ステータス遷移 | 「調理中」→「提供済み」への更新のみ（受理・確認中の判断はホールスタッフの権限であり、厨房スタッフの操作範囲外） |
| 反映速度 | ホールスタッフの受理操作から一定時間以内にキッチンディスプレイへ反映されること（5.1参照） |

## 5. 非機能要件

### 5.1 性能要件

| 項目 | 要件 | 計測条件 |
|------|------|---------|
| 画面表示レスポンス | 3秒以内 | 通常のピーク時アクセスを想定（同時接続数はTBD、要確認） |
| 注文確定・受理からの各画面反映までの遅延 | 10秒以内 | 客の確定操作→ホールスタッフ画面、ホールスタッフの受理操作→キッチンディスプレイ、それぞれについて適用（v1.1で対象を明確化） |

| 同時更新の整合性 | 複数のホールスタッフ・厨房スタッフが同一注文を同時に操作しても状態不整合が発生しないこと | 排他制御の具体的な方式は設計フェーズで決定（TBD、v1.1で追加） |

### 5.2 セキュリティ要件

| 項目 | 要件 |
|------|------|
| 認証方式 | オーナー用メニュー管理画面：ID／パスワード認証必須。客向け画面：Phase1は認証なし（匿名利用）。ホールスタッフ・厨房スタッフ用画面：店舗共有アカウント等での簡易認証を想定（詳細は設計フェーズ） |

| R-005 | v1.1で注文修正・取消・品切れ対応・ホールスタッフ画面分離を追加した結果、Phase1のスコープが初版時点より増加した。予算（500〜800万円）・納期（1ヶ月）は初版時点の想定のままであり、実態と乖離している可能性が高い | 高 | 高 | 高 | 基本設計着手前に追加スコープを踏まえた工数再見積りを行い、必要であれば予算・納期の再協議、またはPhase1内でのMust／Should再仕分けを発注者と行う（v1.1で追加） |

### 9.2 制約事項・前提条件

- 予算上限（概算）：800万円程度（要確認、v1.1のスコープ増加により再見積り対象）
- リリース希望日：要件定義確定から1ヶ月以内（厳守希望。9.1のR-005を踏まえ、状況次第で発注者と再協議する）
- 決済機能は対象外（店頭決済を維持）
- 単一店舗導入だが、将来の他店舗展開・店内飲食対応を見据えた設計とする（v1.1で店内飲食を追記）

### 9.3 本フェーズで検証しないこと（v1.1で新設）

本プロジェクトは実店舗での検証結果や実際の導入効果を保証するものではなく、以下は本書のUAT・受入判断の評価対象に含めない。

- 通信障害発生時の実運用対応
- 実際の混雑状況下でのUX・スループット
- スタッフへの操作教育・定着
- 衛生管理運用（受け渡し時の衛生管理等）
- 決済・会計運用（Phase1では店頭決済のみのため対象外）

## 10. スコープ変更管理ルール

### 10.1 変更管理プロセス

| ステップ | 内容 | 期限 | 担当 |
|---------|------|------|------|
| ① 変更申請 | 変更要望を「変更要求書（CR）」に書面で提出（口頭・チャットのみは無効） | 随時 | 発注者 |
| ② 影響分析 | 受注者が工数・コスト・スケジュールへの影響を提示 | 申請から3営業日以内 | 受注者 |
| ③ 承認判断 | 発注者（オーナー）が承認・却下・保留を決定。Phase1.5／Phase2送りの場合はその旨を明記 | 影響分析提示から3営業日以内 | 発注者 |
| ④ 契約更新 | 承認された変更は契約変更書または注文書追記として文書化 | 承認後速やかに | 双方 |
| ⑤ 実施 | 契約更新完了後に変更作業着手 | 契約更新後 | 受注者 |

### 10.2 変更の種類と対応方針

| 変更種別 | 対応方針 |
|---------|---------|
| スコープ追加（新機能・新画面） | 必ず影響分析・承認・契約追記のプロセスを経る。1ヶ月納期内での追加は原則不可とし、Phase1.5以降で対応 |
| スコープ削減（機能削除） | 双方合意の上でスコープ変更書を作成。コスト精算方針も明記 |
| 仕様変更（既存機能の挙動変更） | 軽微な場合は変更ログに記録して合意。大きい場合は上記プロセス |
| バグ修正 | 仕様通りでない動作の修正はスコープ変更として扱わない（無償対応） |

### 10.3 検収・契約関連事項

| 項目 | 内容 |
|------|------|
| 検収基準 | Phase1で定義した機能要件（Must）がUATで正常動作することをもって検収完了の基本基準とする。あわせて、11.5の代表検証シナリオで対応しきれなかった例外・制約が生じた場合も、それ自体を検証記録として残し、Phase1.5以降の設計判断に活用する（合否判定と検証記録の両立、v1.1で追加） |

### 11.5 代表検証シナリオ（UAT対象、v1.1で新設）

企画書（P002／mobile-order）の検証方針を踏まえ、以下の代表シナリオをUATの評価対象とする。

| # | シナリオ | 確認観点 |
|---|---------|---------|
| 1 | 通常注文（カスタマイズ含む）→受理→調理→提供 | 各画面（客／ホールスタッフ／厨房スタッフ）で注文内容・状態が一致するか |
| 2 | 客が「確認中」の間に注文内容を修正する | 修正内容がホールスタッフの受注確認画面に反映され、変更履歴に記録されるか |
| 3 | 客が「確認中」の間に注文を取り消す | 取消がホールスタッフ・厨房スタッフ双方の画面から見えなくなり、履歴に残るか |
| 4 | 受理後に対象商品が品切れになる | ホールスタッフの受注確認画面で該当注文がハイライト表示され、対応操作ができるか |

> 4シナリオのいずれかで例外を処理しきれない、または操作負担が口頭運用を上回ると判断された場合も、10.3の通り「検収不合格」として終わらせるのではなく、その条件・原因を検証記録として残し、Phase1.5以降の設計判断に活用する。
