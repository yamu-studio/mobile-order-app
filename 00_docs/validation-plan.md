# 検証計画

## 問いと成功条件

架空の単一店舗で、注文・店舗受理・厨房処理・受取待ち・提供完了を、修正・取消・品切れが起きても同じ注文内容と状態で追跡できるかを確認する。実店舗の効果や一般利用者の評価を測定する計画ではない。

成功条件は、下表の代表シナリオについて、期待する状態・明細・変更履歴・各ロールの画面が一致し、禁止操作が拒否されることである。成立しない経路は条件と原因を残し、成功扱いにしない。期待値は[詳細設計書](02_詳細設計書.md)5・8章、画面表示は[デザイン設計書](03_デザイン設計書.md)14章、DB制約は[データベース設計書](04_データベース設計書.md)を正本とする。

## 検証条件

| 項目 | 固定する条件 |
|---|---|
| 対象 | テイクアウト、単一の架空店舗、架空の商品・注文。決済と実利用者データは使わない |
| ロール | 注文者、店舗スタッフ、厨房担当、管理者。各画面と操作権限を分ける |
| データ | 商品、オプション、品切れ状態、注文番号、注文明細、状態・変更履歴を識別できる架空データ |
| 環境 | 実施時のcommit、Node.js・npm、OS、依存関係、起動方法を結果欄に記録する |
| 比較対象 | 同じ注文についての画面間の内容・状態・履歴。実店舗の待ち時間や人件費を比較対象にしない |

## 代表シナリオ

| ID | 入力・操作 | 確認する結果 | 状態 |
|---|---|---|---|
| S1 通常注文 | 客が商品・オプションを確定し、ホールが確認・受理、厨房が受取待ち、ホールが会計・受け渡し確認後に提供済みにする | 受付番号・税込合計・明細が全画面で一致。`received→reviewing→preparing→ready→served`の履歴が順に残り、厨房から提供済み更新はできない | 未実施 |
| S2 修正 | `received`/`reviewing`で客が数量・オプションを変える。古い価格のカートと受理後の修正も試す | 修正後は`received`に戻り再確認が必要。価格変更は再確認まで確定せず、`preparing`以降の客修正は409。旧・新明細と金額が履歴で追える | 未実施 |
| S3 取消 | 客が受理前に取消。別注文では受理後に客取消を試し、ホールが理由付きで取消 | 受理前取消は状態と履歴に残り通常のホール一覧から外れる。未受理注文は厨房一覧に現れない。受理後の客取消は409、ホール取消は厨房通知に残る | 未実施 |
| S4 品切れ | 管理者が注文前・注文確定と競合する時・受理後に売切れへ切り替える。ホールが警告を対応する | 売切れ商品の新規注文・修正での追加は拒否。既存の未完了注文には警告と履歴が残り、未解決時は受理・受取待ち・提供済みへ進めない。提供不可なら受理前は客修正・取消、受理後はホール取消 | 未実施 |
| S5 更新競合・冪等性 | 同じ注文に同じversionで修正・受理・取消を競合させ、同一冪等キーで注文確定を再送する | 競合する更新は1件のみ成功し、他方は409後に最新状態を表示。注文・金額・履歴・警告に欠落や重複がなく、同一入力の再送では注文が増えない | 未実施 |
| S6 匿名注文の再照会 | Cookieを失った客が受付番号と照会コードで復旧。誤コード・番号のみ・旧コード・他注文も試す | 正しい組だけ当該注文への権限を付与。失敗応答は存否を明かさず、反復入力は429。再発行後は旧コードで復旧できない | 未実施 |
| S7 ロールと管理 | 各スタッフがログインし、商品・オプション・アレルゲン・受付可否を管理する。別ロールの更新APIも直接呼ぶ | 管理変更が公開メニューに反映され、販売停止はS4と同じ警告を作る。ホール・厨房・管理者の禁止操作は403、未認証は401。ログアウト後は更新できない | 未実施 |

S1〜S4は主要業務シナリオ、S5は整合性、S6は匿名注文のアクセス権、S7は管理とロール分離の確認である。全シナリオで読み込み中・空・通信失敗時の表示、409後の再取得、操作成功後の他ロール画面への通常10秒以内の反映を確認する。受入判断では各Must機能を少なくとも1シナリオに対応付け、該当する期待値が満たされないものを未達として記録する。

| 要件定義書のMust機能 | 主な確認シナリオ |
|---|---|
| F-001〜F-007（閲覧・選択・注文・追跡） | S1、価格と品切れはS2・S4 |
| F-008〜F-009（客の修正・取消）、F-018（再照会） | S2、S3、S6 |
| F-010〜F-014（ホールの確認・受理・警告・履歴・受け渡し） | S1、S3、S4、S5 |
| F-015〜F-016（厨房の一覧・受取待ち更新） | S1、S3、S4 |
| F-020〜F-024（商品・オプション・販売可否・アレルゲン・受付可否） | S4、S7 |

## テストと証拠

| 段階 | 確認内容 | 証拠 |
|---|---|---|
| 実装時 | Vitestで入力検証、状態遷移、権限拒否、変更履歴、競合など重要な規則を単体・結合テストで確認 | 対象ケース、コマンド、成功・失敗、関連PR |
| 実装時 | Playwrightで注文者→店舗→厨房の主要経路をE2Eで確認 | 実行条件、画面・データの記録、結果 |
| シナリオ検証時 | S1〜S7で期待と実際を同一注文番号・データ条件で比較 | 本書の結果欄、テストログ・画面記録への参照 |
| 振り返り時 | 達成・未達と操作上の摩擦、実務へ適用する際の未検証条件を分ける | 本書の結果欄、振り返りIssue、READMEの制約 |

## 実施コマンド

現在のpackage.jsonには`dev`・`lint`・`build`・`start`がある。初期の確認コマンドは`npm ci`、`npm run lint`、`npx tsc --noEmit`、`npm run build`とする。採用済みのVitest・Playwrightはまだ未導入のため、テスト用scriptと実行コマンドは実装時に追加・記録する。ここに記載したコマンドは実行結果ではない。

## 結果の記録先と限界

実施後は各シナリオの条件、期待、観測した事実、解釈、証拠パス、未検証事項を本書へ追記する。GitHubのシナリオ検証Issueに関連PRと結果箇所をリンクする。現時点の全シナリオは未実施であり、通信障害、混雑、端末差、実店舗スタッフの教育、決済、実利用者の操作は未検証である。これは架空検証の受入条件であり、実在の発注者による検収記録ではない。
