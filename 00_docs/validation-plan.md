# 検証計画

## 問いと成功条件

架空の単一店舗で、注文・店舗受理・厨房処理・提供完了を、修正・取消・品切れが起きても同じ注文内容と状態で追跡できるかを確認する。実店舗の効果や一般利用者の評価を測定する計画ではない。

成功条件は、下表の代表シナリオについて、期待する状態・明細・変更履歴・各ロールの画面が一致し、禁止操作が拒否されることである。成立しない経路は条件と原因を残し、成功扱いにしない。実施前に確定していない業務ルールは、[briefの未決事項](brief.md#設計に渡す判断)と設計Issueで決める。

## 検証条件

| 項目 | 固定する条件 |
|---|---|
| 対象 | テイクアウト、単一の架空店舗、架空の商品・注文。決済と実利用者データは使わない |
| ロール | 注文者、店舗スタッフ、厨房担当、管理者。各画面と操作権限を分ける |
| データ | 商品、オプション、品切れ状態、注文番号、注文明細、状態・変更履歴を識別できる架空データ |
| 環境 | 実施時のcommit、Node.js・npm、OS、依存関係、起動方法を結果欄に記録する |
| 比較対象 | 同じ注文についての画面間の内容・状態・履歴。実店舗の待ち時間や人件費を比較対象にしない |

## 代表シナリオ

| ID | 入力・操作 | 確認する結果 | 状態 |
|---|---|---|---|
| S1 通常注文 | 注文者が商品・オプションを選び確定、店舗が確認・受理、厨房が提供済みにする | 受付番号、明細、`受付済`→`確認中`→`調理中`→`提供済み`、各画面・履歴が一致する | 未実施 |
| S2 修正 | 受理前に注文者が数量・オプション等を変更し、店舗が確認する。受理後にも同じ操作を試す | 受理前の変更のみ反映され、変更履歴が残る。受理後の自己修正は拒否される | 未実施 |
| S3 取消 | 受理前に注文者が取り消し、店舗と厨房から対象注文の扱いを確認する。受理後にも取消を試す | 取消状態と履歴が残り、調理対象へ進まない。受理後の自己取消は拒否される | 未実施 |
| S4 品切れ | カート投入前・注文確定前・受理後に商品を売り切れへ切り替える | 注文できない商品を選べず、既存の未完了注文は店舗側で警告される。受理後の具体対応は設計で決めた規則と照合する | 未実施 |
| S5 更新競合 | 同じ注文を複数画面からほぼ同時に変更・受理する | 状態と履歴に矛盾が残らず、競合結果を利用者が把握できる。方式と期待値は設計で確定する | 未実施 |

S1〜S4はMVPの主要シナリオ、S5は整合性のリスク確認である。失敗経路の入力条件・期待結果は設計時に追記する。

## テストと証拠

| 段階 | 確認内容 | 証拠 |
|---|---|---|
| 実装時 | Vitestで入力検証、状態遷移、権限拒否、変更履歴、競合など重要な規則を単体・結合テストで確認 | 対象ケース、コマンド、成功・失敗、関連PR |
| 実装時 | Playwrightで注文者→店舗→厨房の主要経路をE2Eで確認 | 実行条件、画面・データの記録、結果 |
| シナリオ検証時 | S1〜S5で期待と実際を同一注文番号・データ条件で比較 | 本書の結果欄、テストログ・画面記録への参照 |
| 振り返り時 | 達成・未達と操作上の摩擦、実務へ適用する際の未検証条件を分ける | 本書の結果欄、振り返りIssue、READMEの制約 |

## 実施コマンド

現在のpackage.jsonには`dev`・`lint`・`build`・`start`がある。初期の確認コマンドは`npm ci`、`npm run lint`、`npx tsc --noEmit`、`npm run build`とする。採用済みのVitest・Playwrightはまだ未導入のため、テスト用scriptと実行コマンドは実装時に追加・記録する。ここに記載したコマンドは実行結果ではない。

## 結果の記録先と限界

実施後は各シナリオの条件、期待、観測した事実、解釈、証拠パス、未検証事項を本書へ追記する。GitHubのシナリオ検証Issueに関連PRと結果箇所をリンクする。現時点の全シナリオは未実施であり、通信障害、混雑、端末差、実店舗スタッフの教育、決済、実利用者の操作は未検証である。
