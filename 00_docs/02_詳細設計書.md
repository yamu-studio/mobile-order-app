## 1. 設計判断と範囲

現行のPhase1は匿名のデモ注文を、客・ホール・厨房・管理者が同じ永続データで扱う。実在店舗への送信、実際の提供、実利用者の個人情報収集はまだ行わない。次の実店舗初回利用では、同じ基本構造で実注文を受け、店頭支払いと既存の会計・領収書発行手段を使う。実店舗の情報・運用を確認するまでは公開しない。店内飲食、会員、POS自動連携、プッシュ通知は初回利用の対象外とする。

**決済の判断**：要件定義書1.4・F-006・7章では、店頭決済を維持し、導入コストと審査期間を避けるため、オンライン決済をPhase1から除外している。実店舗初回利用でも匿名注文＋受け取り時の店頭支払いとし、会計記録・領収書発行は既存の店頭手段で扱う。注文の税込合計は支払済みを意味しない。後にオンライン決済が必要になればStripeを候補とし、決済・取消・返金・Webhook・会計の要件を別途定義する。

**技術方針**：DBは開発時Docker上のPostgreSQL、スタッフ認証は同DBに保存する独自実装とする。Next.js 16.3.6、React 19.2.8、TypeScript、Tailwind CSS、npmは現行基盤を使う。DB接続ライブラリ・マイグレーションツールの選定は実装開始時に行い、SQLの制約とトランザクションの意味を維持する。Vitest・Playwrightは要件の検証方針であり、現時点で未導入。

## 2. 全体構成

```text
客ブラウザ ─┐
ホール端末 ─┼─ HTTPS ─ Next.js App Router ─ 業務サービス ─ PostgreSQL（Docker）
厨房端末 ──┤           │                    │
管理者端末 ─┘           └─ Route Handler      └─ 認証・注文・商品・履歴
```

- `app` のページは表示、Route Handlerは入力受付とレスポンスを担当する。認証・認可・金額計算・状態遷移・DB更新はサーバー側の業務サービスに集約し、画面からDBへ直接接続しない。
- PostgreSQLはDocker Composeで起動し、永続化ボリューム、ヘルスチェック、バージョン固定、環境変数からの接続設定を持つ。DBポートは開発機からのみ到達可能にし、秘密情報はリポジトリに記録しない。Next.jsは現行のnpm開発環境で起動する。
- 既存DBへの変更は番号付きマイグレーションで管理し、初期の架空メニューとロール別テストアカウントは開発用シードで投入する。シードに本番用パスワードは置かない。
- 将来のSupabase移行に備え、業務サービスが認証プロバイダーと注文リポジトリの境界を介してデータにアクセスする。内部の主体は`actorId`と`role`で表し、PostgreSQLのユーザーIDやセッショントークンを画面・業務ルールへ漏らさない。切り替え時には認証プロバイダー実装、セッション移行、DBアクセスと権限ポリシーを再設計・再検証する。無変更で移行できるとは扱わない。

## 4. 認証・認可

| 主体 | 閲覧 | 更新 | 禁止操作 |
|---|---|---|---|
| 匿名の客 | 公開メニュー、自分のセッションで作成した注文 | 注文作成、受理前の自分の注文の修正・取消 | 他人の注文、受理、提供、商品管理 |
| ホール | 対象店舗の全注文・変更履歴・品切れ警告 | 受付確認、受理、品切れ対応、必要時のスタッフ取消、受取待ちから提供済み、注文受付の一時停止・再開 | 商品管理、厨房の調理完了更新 |
| 厨房 | 調理中の注文と必要な明細・取消通知 | 調理中から受取待ち | 注文受理、提供済みへの更新、客の代理修正、商品管理 |
| 管理者 | 商品・オプション・アレルゲン | 商品管理・売切れ切替、注文受付の一時停止・再開 | ホール・厨房の注文状態更新 |

スタッフはロールごとに分けたID・パスワードでログインする。Phase1では管理画面からのアカウント登録は設けず、管理用の初期登録手順で発行・停止する。共有IDは操作主体の追跡を弱めるため採用しない。パスワードは要件の最低条件である8文字以上・英数字混在とし、サーバーで検査する。保存はソルト付きの低速ハッシュとし、平文・可逆暗号化・ログ出力を禁止する。ログイン失敗は同一ID・送信元を単位に回数制限し、応答はIDの存否を明かさない。

スタッフのセッションは十分に長い乱数トークンを発行し、DBにはそのハッシュと`actor_id`、有効期限、失効時刻を保存する。ブラウザには`HttpOnly`、`Secure`、`SameSite=Lax`、`Path=/`のCookieを設定し、ログアウトと期限切れで無効にする。ロール変更・アカウント停止時も既存セッションを失効させる。トークンはURL、クライアント側ストレージ、ログへ出さない。

匿名の客には個人情報を要求しない。注文送信前にランダムなゲストセッションを作り、保護したCookieとDB側のトークンハッシュを使う。注文ごとに端末セッションへのアクセス権を保存し、追跡・修正・取消ではサーバーが権限を検査する。受付番号だけでは注文にアクセスできない。Cookieを失った場合は、注文完了時に一度だけ示した受付番号と秘密の照会コードを入力し、検証後に新しいセッションへアクセス権を付与する。照会コードはDBにハッシュのみを保存し、推測困難な乱数で生成する。コードをURLやログに含めず、照合には回数制限を設ける。Cookieとコードの両方を失った場合は、客画面からは復旧できないことを明示する。

画面の非表示だけでは認可しない。すべてのRoute Handlerでセッション、ロール、対象注文の所属を検査し、Cookieを使う更新系はOrigin検査を行う。想定外のContent-Type、クロスサイト要求、入力超過を拒否する。DBアクセスはパラメータ化し、HTMLに任意入力をそのまま埋め込まない。権限なしは403、未認証は401、所有関係を隠す必要がある注文取得は404とする。

## 5. 注文の状態と競合

| 現在状態 | 操作と実行者 | 次状態 | 条件・効果 |
|---|---|---|---|
| なし | 注文確定・客 | 受付済 | 現行メニューで再計算し、注文・明細・履歴を同時作成 |
| 受付済 | 内容を確認・ホール | 確認中 | 注文内容を画面で確認したことを記録 |
| 受付済／確認中 | 修正・客 | 受付済 | 受理前のみ。明細・合計・変更履歴を同時更新し、ホールの再確認を要求 |
| 受付済／確認中 | 取消・客 | 取消 | 変更履歴を残し、以後の操作を拒否 |
| 確認中 | 受理・ホール | 調理中 | 最新の明細と品切れ警告を確認し、厨房一覧へ反映 |
| 調理中 | 調理完了・厨房 | 受取待ち | 未解決の品切れ警告がない場合のみ。客・ホールへ反映 |
| 受取待ち | 会計・受け渡し確認・ホール | 提供済み | 既存の店頭会計手段で会計を確認してから更新 |
| 受付済／確認中／調理中／受取待ち | スタッフ対応で取消・ホール | 取消 | 理由必須。厨房には取消通知を表示し、調理一覧から除く |

要件の「確定時は受付済」と「受理は確認中→調理中」を両立させるため、ホールの「内容を確認」操作を受付済→確認中の明示的な遷移とする。確認中でも受理前なら客は修正・取消できる。客の修正後は確認中から受付済へ戻し、ホールによる再確認を必須にする。これにより古い明細を受理しない。取消・提供済みは終端状態とする。実店舗の初回利用を見据え、調理完了の「受取待ち」を追加し、厨房と受け渡し担当の責任を分ける。受理後の明細変更は客に許可せず、ホールでの対応内容は理由とともに履歴へ残す。受理後の代替品への自動置換は設けない。

各注文に単調増加する`version`を持たせる。更新要求は画面で見たversionを必須とし、サーバーは注文行をトランザクション内でロックして、状態・version・権限と未解決警告を再確認する。注文作成・修正と管理者の商品・選択肢・価格・アレルゲン編集では、対象商品行をID順に先にロックし、その後に必要な注文行をロックする。成功時だけ注文、明細、履歴、警告対応を一括コミットし、versionを1増やす。古いversionは409で拒否し、最新データを再取得させる。二重送信対策として注文確定にはクライアント生成の冪等キーを使い、ゲストセッション内で一意にする。同じキーの再送は元の注文を返し、異なる内容なら409とする。履歴の挿入に失敗した更新は全体をロールバックする。

履歴は`created`、`reviewed`、`amended`、`accepted`、`ready`、`served`、`canceled`、`stock_alert_opened`、`stock_alert_resolved`を時刻順に保存する。修正は変更前後の明細・税込合計のスナップショット、実行者のロールとID、理由、versionを記録する。ホールは全履歴、客は自分の注文の状態・内容変更履歴、厨房は調理に関係する変更・取消通知を閲覧できる。管理者には注文履歴を公開しない。

## 6. 商品・品切れ・価格

- 商品はカテゴリ、説明、画像参照、税込基本価格、販売可否を持つ。オプションは商品に属するグループ（例：サイズ、ミルク）と単一選択肢に分け、選択肢の追加料金は0円以上とする。必須グループには各1件の選択を要求する。アレルゲンは商品の不変部分と選択肢ごとに登録し、選択内容に応じて表示する。「オプション変更はアレルギー対応を保証しない」を併記し、実店舗の情報は店舗が確認する。
- カート内の金額は参考値。確定・修正時はサーバーが最新の価格で`単価 = 基本価格 + 選択オプションの追加料金`、`小計 = 単価 × 数量`、`合計 = 小計の総和`を整数円で計算する。金額・数量の上限を設け、負数とオーバーフローを拒否する。価格がカート表示から変わった場合は確定を止め、最新金額を示して再確認を求める。
- 注文明細には注文時点の商品名・単価・選択肢名・追加料金・アレルゲン表示をスナップショット保存する。商品編集・販売停止後も過去注文が変化しない。商品・オプションは参照済みなら物理削除せず非公開化する。
- 管理者が商品を売り切れにすると、新規注文・修正での追加を拒否する。未完了注文の該当商品に品切れ警告を作り、ホール一覧に表示する。既存の注文内容は自動変更しない。既に調理中の注文もホールに表示し、厨房の当該注文にも警告を表示する。
- ホールは現物を提供可能と確認した場合に理由付きで警告を「対応済」にできる。提供不可なら客と調整し、受理前は客に修正・取消を案内し、受理後はホールが理由付きで取消する。修正で該当商品が外れた場合、取消した場合、商品が販売中に戻った場合は警告を対応理由とともに自動解消する。警告が未対応の注文は受理・受取待ち・提供済み操作を拒否する。代替品の自動提案や受理後の明細差し替えは行わない。実店舗での連絡手段と現場手順は公開前に確定する。

## 7. データ設計

物理的な列・キー・索引・削除方針は[データベース設計書](04_データベース設計書.md)を正本とする。PostgreSQLの主キーはUUID、日時は`TIMESTAMPTZ`、金額は非負の整数円で保存する。単一店舗でも`store_id`を商品・注文・スタッフに持たせ、別店舗の混入を防ぐ。初回実店舗利用でも本アプリは店頭支払情報、カード情報、顧客氏名・連絡先、会員テーブルを保存しない。

| テーブル | 主な列 | 制約と用途 |
|---|---|---|
| `stores`、`store_opening_hours`、`store_ordering_events`、`categories` | 店舗、注文受付可否、営業時間と切替履歴、カテゴリ、受取場所 | 店舗単位で管理 |
| `staff_accounts`、`staff_local_credentials`、`staff_sessions` | ロール別アカウント、ローカル認証情報、セッション | 認証方式と業務上の主体IDを分離 |
| `guest_sessions`、`order_access_grants`、`order_access_codes` | 匿名端末、注文への権限、照会コードのハッシュ | Cookie喪失時は受付番号＋秘密コードで新セッションへ権限を付与 |
| `products`、`option_groups`、`option_choices` | 商品・オプションの現在の管理情報 | 参照中の商品・選択肢は廃止しても保持 |
| `allergens`、`product_allergens`、`choice_allergens` | 商品不変部分と選択肢のアレルゲン | 注文時に表示文を保存 |
| `orders` | 受付番号、状態、version、税込合計、受理・受取待ち・完了時刻 | 6状態。支払状態は持たない |
| `order_items`、`order_item_choices` | 現行明細と選択肢、注文時点の名称・価格・アレルゲン表示 | 現行明細を正規化し、表示値は意図的に複製 |
| `order_events` | 状態変更・修正・取消・品切れ対応の変更前後 | 追記のみの履歴 |
| `stock_alerts`、`order_requests` | 品切れ対応、注文確定の冪等性 | 未解決警告の重複と二重注文を防ぐ |

受付番号は表示識別子であり、秘密情報として扱わない。取消は状態変更、提供済み注文のアーカイブは一覧からの除外、商品の廃止は論理削除とする。注文・イベントの物理削除は保持期間を確定した後に集約単位で実施する。実店舗初回利用の保持期間は店舗と運用方針を確認して公開前に決める。将来の会員・オンライン決済・店内飲食は、その時点で追加マイグレーションを設計する。

## 8. APIと画面更新

| 経路案 | 方法 | 内容・権限 |
|---|---|---|
| `/api/menu` | GET | 公開中の商品、カテゴリ、選択肢、販売可否 |
| `/api/orders` | POST | 匿名セッションで注文確定。冪等キー必須 |
| `/api/orders/[id]` | GET/PATCH | 所有する注文の取得・受理前修正 |
| `/api/orders/[id]/cancel` | POST | 客が受理前の自分の注文を取消。DB行は削除しない |
| `/api/orders/recover` | POST | 受付番号と秘密の照会コードで新しい匿名セッションへアクセス権を付与 |
| `/api/orders/[id]/access-code` | POST | 有効な匿名セッションから照会コードを再発行。旧コードは無効化 |
| `/api/staff/orders` | GET | ホールの受注一覧、品切れ警告 |
| `/api/staff/orders/[id]/review` | POST | ホールが内容確認 |
| `/api/staff/orders/[id]/accept` | POST | ホールが受理 |
| `/api/staff/orders/[id]/serve` | POST | ホールが店頭会計・受け渡しを確認して提供済みにする |
| `/api/staff/orders/[id]/cancel` | POST | ホールが理由付き取消 |
| `/api/staff/store/accepting-orders` | POST | ホールまたは管理者が受付を一時停止・再開し、履歴を記録 |
| `/api/staff/stock-alerts/[id]/resolve` | POST | ホールが理由付きで対応済みにする |
| `/api/kitchen/orders` | GET | 厨房の調理中一覧と必要な通知 |
| `/api/kitchen/orders/[id]/ready` | POST | 厨房が調理完了として受取待ちへ進める |
| `/api/admin/products`、`/api/admin/products/[id]` | GET/POST/PATCH | 管理者の商品登録・編集・販売可否切替 |
| `/api/auth/login`、`/api/auth/logout` | POST | スタッフのログイン・ログアウト |

更新APIは入力検証と権限確認を済ませ、業務サービスのトランザクションを呼ぶ。成功は更新後の注文とversion、入力不正は400、権限違反は401/403、欠損または所有外は404、状態・version・価格変動・冪等キー不一致は409を返す。内部エラーの詳細はレスポンスに出さない。`GET`は認証に応じて毎回最新DBを参照し、個別注文やスタッフ一覧を共有キャッシュに載せない。

客の追跡、ホール一覧、厨房一覧は画面表示中に3秒間隔で再取得し、非表示タブでは間隔を延ばし、復帰時に即時更新する。注文確定・修正・取消・受理・受取待ち・提供済みの成功時は該当画面を即時再取得する。通常時の画面反映10秒以内を目標とするが、通信断中の保証はしない。再取得失敗時は最終更新時刻と「更新できていない」表示を出し、古い状態での更新を安全に失敗させる。

## 9. 検証観点と残る判断

| 検証計画 | 確認する仕様 |
|---|---|
| S1 通常注文 | 受付済→確認中→調理中→受取待ち→提供済み、税込金額・明細・各画面・履歴が一致 |
| S2 修正 | 受付済／確認中で修正可能、修正後は再確認が必要、受理後は拒否 |
| S3 取消 | 受理前の客取消、受理後の客取消拒否、スタッフ取消後の厨房通知 |
| S4 品切れ | 選択不可、確定時の再検証、未完了注文の警告、未対応時の受理・提供拒否 |
| S5 競合 | 同時修正・受理・取消で一方のみ成功、409後の再取得、履歴欠落なし |
| S6 匿名注文の再照会 | 受付番号＋正しい秘密コードだけで新セッションへ権限を付与し、誤入力と連続試行を拒否 |

Vitestで状態遷移、権限、金額再計算、冪等性、同時更新と履歴の原子性を確認し、PostgreSQLを使う結合テストで行ロックと一意制約を確認する。Playwrightで客・ホール・厨房の主要経路を確認する。実施結果は[検証計画](validation-plan.md)に記録し、実行前に成功したとは記載しない。

実店舗公開前に確定する事項は、受理後の品切れでの連絡手段・厨房への声掛け、営業時間と想定負荷、注文・履歴の正式な保持期間、スタッフ画面の最終UI、アレルゲンの実データ確認、店頭会計との突合手順である。調理完了は厨房、会計・受け渡し確認後の提供済み更新はホールの担当とする。

今回承認された「受取待ち」を[要件定義書](01_要件定義書.md)と[検証計画](validation-plan.md)にも反映した。6状態の実装・テストは今後行う。
