# Project Brief

## 成果物と利用場面

架空の単一店舗を題材に、テイクアウト注文から店舗の受理、厨房処理、提供完了までを同じ注文データで追えるWebアプリと検証記録を作る。実在店舗の業務改善や利用者への提供を実施・確認した企画ではない。要件の詳細は[要件定義書](01_要件定義書.md)、客側の参考画面は[デザイン設計書](03_デザイン設計書.md)を参照する。

## 問い

単一店舗のテイクアウト向けモバイルオーダーで、注文から店舗確認、厨房処理、提供完了までの流れを、注文漏れ・修正・取消・品切れに対応しながら個人開発で検証可能な形にできるか。

## 仮説

注文内容と状態を一元化し、注文者・店舗スタッフ・厨房担当が必要な情報だけを確認できれば、架空の業務シナリオで情報の食い違いや伝達漏れを減らせる可能性がある。実際の業務効率の改善は本企画では測定しない。

## 想定利用者と代表操作

| ロール | 代表操作 |
|---|---|
| 注文者 | 架空メニューから商品とオプションを選び、匿名で注文し、受付番号で状態を確認する。店舗が受理する前だけ修正・取消できる。 |
| 店舗スタッフ | 新規・修正・取消を確認し、注文を受理する。品切れが発生した注文への対応を判断する。 |
| 厨房担当 | 受理済み注文を確認し、調理中から提供済みへ更新する。 |
| 管理者 | 商品・価格・オプション・アレルゲン・品切れを管理する。 |

代表シナリオは通常注文、受理前の修正・取消、品切れ、同時更新である。各ロールの画面と権限、注文の変更履歴を同じ注文について照合する。

## MVP

- テイクアウト専用、匿名注文、受付番号による注文追跡。
- 店舗画面で新規注文、修正・取消を確認して受理する。
- 厨房画面で受理済み注文を確認し、調理中から提供済みへ更新する。
- 管理画面で商品、オプション、アレルゲン、品切れを管理する。
- `受付済`・`確認中`・`調理中`・`提供済み`・`取消`の状態と変更履歴を扱い、代表シナリオを検証する。

## 採用済みの技術と設計対象

現在の`package-lock.json`で確認できる基盤はNext.js `16.3.6`、React／React DOM `19.2.8`、TypeScript `5.9.3`、Tailwind CSS `4.3.3`、npmである。設計工程ではこの採用済み基盤を再選定せず、注文データ・状態更新・認可・画面・テストの具体的な方式を定める。DB・認証・テスト基盤の採用情報は現行repo内で確認できていないため、決定済みの内容がある場合は設計Issueに根拠とともに記録する。

## 非対象

- 決済、会員登録、実店舗リリース、実利用者データ、店内注文、複数店舗、POS連携。

## 設計に渡す判断

| 未決事項 | 判断の担当と影響 |
|---|---|
| 同時更新の整合性と注文履歴の保存・閲覧範囲 | 設計担当が定義。注文内容の食い違いと権限に影響する。 |
| 受理後の品切れ時の対応、受理前の修正・取消の通知 | 企画担当が業務上の扱いを確認し、設計担当が画面・状態への反映を定義する。 |
| 店舗・厨房・管理者の認証方式と禁止操作 | 設計担当が採用済みの技術と要件に合わせて記録する。 |
| モバイル幅のカート・モーダルと参考画像にないスタッフ画面 | デザイン担当が提案し、企画担当がMVPとの整合を判断する。 |

成功条件と証拠は[検証計画](validation-plan.md)を正本とする。未決事項を確認済み・実装済みとして扱わない。
