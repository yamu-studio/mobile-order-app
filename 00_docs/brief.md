# Project Brief

## 成果物と利用場面

架空の単一店舗を題材に、テイクアウト注文から店舗の受理、厨房処理、受取待ち、提供完了までを同じ注文データで追えるWebアプリと検証記録を作る。DB設計は将来の実店舗初回利用まで見据えるが、実在店舗への公開や実利用者データの投入は別の判断とする。要件の詳細は[要件定義書](01_要件定義書.md)、客側の参考画面は[デザイン設計書](03_デザイン設計書.md)を参照する。

## 問い

単一店舗のテイクアウト向けモバイルオーダーで、注文から店舗確認、厨房処理、提供完了までの流れを、注文漏れ・修正・取消・品切れに対応しながら個人開発で検証可能な形にできるか。

## 仮説

注文内容と状態を一元化し、注文者・店舗スタッフ・厨房担当が必要な情報だけを確認できれば、架空の業務シナリオで情報の食い違いや伝達漏れを減らせる可能性がある。実際の業務効率の改善は本企画では測定しない。

## 想定利用者と代表操作

| ロール | 代表操作 |
|---|---|
| 注文者 | 架空メニューから商品とオプションを選び、匿名で注文し、受付番号で状態を確認する。店舗が受理する前だけ修正・取消できる。 |
| 店舗スタッフ | 新規・修正・取消を確認し、注文を受理する。品切れ対応を判断し、店頭会計・受け渡しの確認後に提供済みへ更新する。 |
| 厨房担当 | 受理済み注文を確認し、調理中から受取待ちへ更新する。 |
| 管理者 | 商品・価格・オプション・アレルゲン・品切れを管理する。 |

代表シナリオは通常注文、受理前の修正・取消、品切れ、同時更新である。各ロールの画面と権限、注文の変更履歴を同じ注文について照合する。

## MVP

- テイクアウト専用、匿名注文、受付番号による注文追跡。
- 店舗画面で新規注文、修正・取消を確認して受理する。
- 厨房画面で受理済み注文を確認し、調理中から受取待ちへ更新する。ホール画面で受け渡しを確認して提供済みへ更新する。
- 管理画面で商品、オプション、アレルゲン、品切れを管理する。
- `受付済`・`確認中`・`調理中`・`受取待ち`・`提供済み`・`取消`の状態と変更履歴を扱い、代表シナリオを検証する。

## 採用済みの技術と設計対象

現在の`package-lock.json`で確認できる基盤はNext.js `16.3.6`、React／React DOM `19.2.8`、TypeScript `5.9.3`、Tailwind CSS `4.3.3`、npmである。設計判断として開発時DBはDocker上のPostgreSQL、スタッフ認証は同DBを使う独自セッション方式を採用した。注文データ・状態更新・認可・画面・検証方法は詳細設計書、デザイン設計書、DB設計書、検証計画に記録する。Vitest・Playwrightは検証方針であり、現時点では未導入である。

## 非対象

- アプリ内決済、会員登録、実店舗リリース、実利用者データ、店内注文、複数店舗、POS連携。実店舗初回利用を見据えたDB設計は対象とする。

## 設計判断と残る確認

| 項目 | Phase1架空検証での扱い |
|---|---|
| 同時更新・注文履歴 | 注文version、行ロック、変更イベント、ロール別閲覧を詳細設計書とDB設計書に定義した。 |
| 品切れ・修正・取消 | ホールの警告、進行停止、受理前の客修正・取消、受理後のホール取消、厨房通知を定義した。 |
| スタッフ認証・禁止操作 | 独自セッションとサーバー側のロール別認可を定義した。 |
| モバイルとスタッフ画面 | デザイン設計書にPhase1の画面・状態・レスポンシブ方針を定義した。 |

成功条件と証拠は[検証計画](validation-plan.md)を正本とする。これらは設計判断であり、実装・テストの完了を意味しない。実店舗利用前の未決事項は[要件定義書11.4](01_要件定義書.md#114-設計判断の状態と実店舗公開前の未決事項)に分けて記録する。
